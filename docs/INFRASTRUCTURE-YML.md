# infrastructure.yml field reference

`infrastructure.yml` is the file the Azure Local Toolkit, azurelocal-ztp and the other Azure Local tools read. Trailwright writes it in the layout of the toolkit's schema 5, with `_metadata.schema_version: 5.6.31`. The key names and the nesting are the schema's; Trailwright adds none of its own.

> **Known gap (checked 2026-11-24).** When you answer the Azure foundation questions, the **Azure virtual networks** table (`landing_zone.networks`) has only `name`, `role` and `resource_group` columns. The toolkit schema requires `address_space` on each entry, so an export that includes that table does not pass the toolkit's `Test-InfrastructureFile.ps1`. Add `address_space` (a list of CIDR blocks) to each network by hand, then run the validator. A design without the Azure foundation is not affected.

The contract is the toolkit's JSON Schema (2020-12) for the file, `config/variables/schema/infrastructure.schema.json` in azurelocal-toolkit. This repository holds a copy at [`apps/trailwright/src/infra/infrastructure.schema.json`](../apps/trailwright/src/infra/infrastructure.schema.json) (`SCHEMA_VERSION` in `src/infra/types.ts` names its version) and publishes the same file with the site at `/schema/infrastructure.schema.json` (from `public/schema`). The toolkit's `templates/infrastructure.master.yml` shows every key with a comment and an example value.

A unit test (`tests/infrastructureSchema.test.ts`) builds the export for every design in `tests/exportProjects.ts` and for every choice a design can make, and validates each against the schema. `npm run build` runs that test first, so the build fails when the exporter and the schema drift apart. The schema itself is the toolkit's: with `AZL_TOOLKIT_ROOT` set (CI checks the toolkit out next to this repository), the same test fails when the vendored copy differs from the toolkit's schema or version, and `npm run schema:sync --workspace apps/trailwright` copies the toolkit's files here, sets `SCHEMA_VERSION` and regenerates the types. The exporter is typed with the types generated from the schema (`npm run schema:types`), so a key the schema does not have does not compile.

## Rules of the export

- **Only what the design knows is written.** A value the design does not hold is left out, never guessed. A design that is not finished therefore gives a file the schema reports as incomplete, and the report names the missing keys.
- **Secrets are never values.** Credentials are `keyvault://<vault>/<secret>` references. The vault is the Key Vault of the instance; the secret names are the ones the toolkit's master template uses (`local-admin-password`, `lcm-password`, `provisioning-admin-password`). Without a vault name the reference is left out.
- **Sections follow the scenario.** A SAN design has no Storage Spaces Direct keys, a local identity design has no `identity.active_directory`, and `disconnected` is written only for disconnected operations.

The separate environment file export is deprecated: `infrastructure.yml` replaces it, and the **Terraform variables** export is the only other file for the deploy automation; see [ENVIRONMENT-FILE.md](ENVIRONMENT-FILE.md). The ARM parameters are their own exports and are no longer repeated in this file.

## Where each value goes

| Section | Keys Trailwright writes | Source in the design |
|---|---|---|
| `_metadata` | `schema_version` (`5.6.31`), `scope` (`trailwright`, a planning scope), `file_version` (`1.0.0`), `generated_by` (`azurelocal-trailwright`) | Fixed |
| `scenario` | `identity`, `storage_architecture`, `storage_connectivity`, `topology`, `connectivity`, `cloud`, `outbound_path`, `os_install`, `deploy_method` | Identity, architecture, network design, hardware, connectivity mode, outbound connectivity, provisioning. A SAN design and a single machine are `switched` |
| `site` | `customer`, `owner`, `name`, `code`; `time_zone` with simplified provisioning | Project: customer, owner, site name, site code; the site time zone of simplified provisioning |
| `environment` | `name`, `type` | The project name as lowercase letters, digits and hyphens (at most 41 characters); Project: environment type |
| `azure` | `tenant_id`, `location`, `subscription_id`, `resource_group`, `hci_resource_provider_object_id`, `custom_location` | Azure resources |
| `key_vaults[]` | `name`, `subscription_id`, `resource_group`, `purpose` (`deployment`) | The Key Vault of the instance, in the subscription and resource group of the instance. It holds the secrets the references of the file name, so it exists before the deployment |
| `cluster` | `name`, `naming_prefix`, `witness.{type, storage_account, path}`, `key_vault.{name, create_new, soft_delete_retention_days}` (`create_new` is `false`: the vault already holds the secrets the file references, so the deployment uses it instead of creating one of the same name), `diagnostics.{storage_account, logs_retention_days, storage_account_type}` | Azure resources: instance name (else the project name, as the ARM parameters), prefix, Key Vault, witness and diagnostic storage accounts. Witness type as in the ARM parameters: two machines get `cloud`; a file share witness is `file_share` with its path |
| `deployment` | `solution_version`, `events_directory` | Project: the release build, when it is a full four-part build; the folder for the run event feeds (a question under "More for infrastructure.yml" on the deployment screen) |
| `nodes[]` | `name`, `network_adapters[]`, `serial_number`; `zone` for rack-aware (an empty zone is Zone1 for the first half, Zone2 for the second, as in the ARM parameters); `storage_ips` when storage Auto IP is off and every address is given; `bmc.ip_address` with simplified provisioning | Hardware, management network, provisioning |
| `nodes[].network_adapters[]` | Every port of the network cards, the same on every machine: `name` (the port name the intents and storage networks use), `slot` (the card label), `port_index` (the order on the card), `vendor`, `model`, `speed_gbps`, `rdma`, `roles` (what the intent of the port carries; `provisioning` is added to the management port with simplified provisioning; a standalone cluster port of a SAN design is `unused`), `ip_assignment`. The management port, the first port of the intent that carries management traffic and listed first, owns the machine's address (`ip_address`) and, when the design has it, its MAC (`mac_address`); its `ip_assignment` is the answer to "How does each machine's management port get its address" (static, DHCP with a reservation as `dhcp_reservation`, or preconfigured). Every other port is `none`. A design without network cards writes the older `nodes[].management` instead, when the machine has an address | Network design (the cards and ports), the machine's address and MAC, and the management address mode. The deprecated `networking.management.ip_assignment` is not written |
| `hardware` | `vendor`, `model`, `cpu_cores`, `memory_gib`, `sbe.*`, `network_cards[]` (`label`, `make`, `model`, `ports[]` with `name`, `speed_gbps`, `rdma`, `role`), `drives.{capacity, cache}` | Hardware: vendor and model (with simplified provisioning and neither given, the validated model chosen there); cores and memory when every machine has the same; the Solution Builder Extension; the network cards of the network design (cluster ports 1 and 2 are `cluster:a` and `cluster:b`); the drive layout for Storage Spaces Direct |
| `networking.management` | `subnet`, `gateway`, `vlan_id`, `dns_servers`, `use_dhcp`, `infrastructure_pool.{start, end}` | Management network. `subnet` is the CIDR of the gateway (else the pool start, else the first machine) with the subnet mask |
| `networking.intents[]` | `name`, `traffic`, `adapters`; `overrides.{qos, adapter, virtual_switch}` only for what the design overrides | Intents. Overrides are numbers and booleans; RDMA `Auto` writes no `network_direct_technology` |
| `networking.storage` | `auto_ip`, `switchless_links` (switchless), `tor_switches`, `layout`, `networks[]` (`name`, `adapter`, `vlan_id`, `subnet`) | Network design, storage VLANs and subnets. Storage Spaces Direct with more than one machine only |
| `networking.cluster_networks[]` | `name`, `adapter`, `vlan_id`, `subnet` | A SAN design: the standalone cluster ports and the cluster subnets, with the names and VLANs (1711, 1712) of the ARM parameters |
| `networking.vlans[]` | `name`, `id`, `subnet` | VLANs; `subnet` is the row of the IP plan with the same name |
| `networking.logical_networks[]` | `name`, `vlan_id`, `address_prefix`, `gateway`, `dns_servers`, `ip_pool.{start, end}` | Software defined networking: the logical networks, when SDN is on |
| `networking.outbound` | `proxy.url`; `arc_gateway.name`; `private_path.*` (`transport`, `virtual_network`, `workload_subnet`, `firewall_subnet`, `firewall_private_ip`, `firewall_port`, `arc_private_link_scope`, `proxy_bypass`) | Outbound connectivity, for the path chosen. The bypass text becomes a list |
| `identity` | `local_admin.{username, password}`; `active_directory.{domain_fqdn, ou_path, lcm_user.{username, password}}` or `local_identity.{dns_server_config, dns_zone, dns_forwarders}` | Identity. Passwords are Key Vault references |
| `storage` | `configuration_mode`, `volumes[]` (`name`, `size_gib`, `resiliency`) for Storage Spaces Direct; `san.{type, infra_volume_lun_id, performance_history_lun_id, luns[]}` for a SAN | Storage |
| `security` | `level`, `drift_control`, `credential_guard`, `smb_signing`, `smb_cluster_encryption`, `bitlocker_boot_volume`, `bitlocker_data_volumes`, `wdac`, `telemetry.{streaming_data, episodic_data_upload, eu_location}` | Security |
| `sdn` | `enabled`; when enabled `prefix`, `dns_records` | Software defined networking |
| `operations` | `update_method`, `backup.{enabled, approach, solution}`, `disaster_recovery.method`, `monitoring.{enabled, log_analytics_workspace, workspace_resource_group, data_collection_rule, data_collection_endpoint, alert_email}` | Operations. The limited-connectivity PowerShell update method is `powershell`. `data_collection_rule` only for an existing rule, `data_collection_endpoint` only with private links |
| `provisioning` | `os_version`; with simplified provisioning `simplified.{site_name, resource_group, maintenance_iso, admin.{username, password}, media_share.{name, host}, ntp.{configuration, server}}` | Provisioning: the software version (else the release build), the site, the provisioning image and the SMB share. `admin.username` is the local administrator of the Identity step, as in the provisioning manifest; its password is a reference into the Key Vault for administrator credentials. A time server gives `ntp.configuration: Manual` |
| `disconnected` | `role`, `base_path`, `domain_suffix`, `ingress.*`, `management.*`, `dns_server`, `time_servers`, `identity.*`, `operator_subscription_name`, `resource_group`, `internal_ca` | Disconnected operations |
| `landing_zone.subscriptions[]` | `name`, `id`, `role` (`azure_local`) | Azure resources: the subscription name |

## What the design holds that has no key

These values stay in the project file and the handoff document; schema 5 has no key for them, so the export leaves them out.

- The release train (for example `2611`) without a full build, and the name of Microsoft's deployment template. The ARM parameters themselves are in the ARM and Bicep exports.
- Rack-aware uplink option, number of racks, ports per node, intent grouping, guest backup network, number of Fibre Channel HBA ports.
- Cores and memory when the machines differ, and the drive count of each node (the drive layout is written).
- Rows of the IP plan that have no VLAN of the same name.
- The proxy server of the simplified provisioning site, and the validated-hardware choice itself (it only stands in for vendor and model).
- Operations: the Update Manager switch, ReFS deduplication monitoring, and the note that Insights creates the data collection rule.
- Free-text notes. They are in the project JSON and the handoff document; never type a secret into a note.

## Required keys Trailwright cannot fill

The schema needs these and the design does not hold them. Add them to the file by hand.

- **A hybrid design:** `networking.cluster_networks` (the network design has cluster ports for a disaggregated design only).
- **Nodes and the cluster IP on DHCP:** `networking.management.gateway`, `networking.management.dns_servers` and each `nodes[].management.ip_address`. The management network step does not ask for them when DHCP is on.
- **MACs:** a planner cannot know the MAC of a port. Trailwright writes `_metadata.scope: trailwright`, a planning scope (schema 5.6.33, owner decision O2): everything the `full` scope requires is required, except the MACs of the ports, which hardware discovery (`Update-InfrastructureYml-FromDiscovery.ps1`) fills in. Set the scope to `full` once discovery has run, so the deployment checks them. The management MAC the design has is written on the management port.
- **Simplified provisioning:** the schema's ZTP scope (`_metadata.scope: ztp`) also needs `hardware.bmc` (the BMC login). Trailwright writes the `trailwright` scope, where it is optional; the Machines and hardware screen asks for it under "More for infrastructure.yml".

## Answers to the questions the screens do not ask

Each screen also shows the catalog questions its own fields do not ask (`EXTRA_QUESTION_IDS` in `src/questions/answers.ts`), under "More for infrastructure.yml". Their answers are saved in the project file as `answers`, a schema 5 document, and the export fills them in where the screens give no value. They are: `environment.owner`, `environment.description`, `site.location`, `tags`, `azure.automation_identity.{type, name}`, `nodes[].{arc_machine_name, rack, rack_position}`, `hardware.gpu.{enabled, model}`, `hardware.bmc.{username, password}`, `hardware.sbe.{package_sha256, package_size_bytes, node_pull_url, bundle_path, version, allow_unvalidated}`, `networking.management.ip_assignment`, `networking.ntp_servers`, `networking.oob.{subnet, gateway}`, `networking.outbound.proxy.bypass`, `identity.active_directory.{netbios_name, domain_controllers, security_groups}`, `identity.entra.groups`, `cluster.deployment_mode`, `provisioning.iso.image_source`, `provisioning.simplified.media_share.host_adapter`, `operations.notifications.emails`, `operations.disaster_recovery.{recovery_vault, target_rpo_minutes, target_rto_minutes}`, `operations.licensing.azure_hybrid_benefit`, `network_devices`, `landing_zone.{resource_groups, networks, virtual_machines, log_analytics.name}` and `devops.{platform, organization, runner.name, runner.type}`.

The question catalog decides what applies from the whole design. An answer to a question that does not apply is not exported (it stays in the project, so changing the design back brings it back): Active Directory answers with local identity, the BMC login without simplified provisioning, the Azure foundation and CI/CD answers unless they are turned on (Azure resources screen). An answer for a machine the design no longer has is dropped. A value the screens give always wins over a stored answer.

Not asked: every other key of the schema, for example `nodes[].network_adapters`, `nodes[].san`, `storage.san.array`, `deployment.*` run settings and `os_configuration`. See [WHAT-TO-COLLECT.md](WHAT-TO-COLLECT.md).

`landing_zone.budgets[]` (5.6.30, the Cost Management budgets) is not written either: the design has no field for it. The optional keys schema 5.6.17 to 5.6.28 added are not written either: the design has no field for them, and the toolkit's Trailwright template (`config/variables/templates/tools/trailwright.yml`) does not list them as keys Trailwright writes. They are `azure.automation_identity.object_id`, `landing_zone.management_groups[].role`, `landing_zone.subscriptions[].billing_scope` and `workload`, `landing_zone.connectivity.bastion.network`, `nat_gateway.*` and `vpn_gateway.point_to_site.{protocols, root_certificate_name, root_certificate}`, `landing_zone.network_security_groups[]`, `landing_zone.networks[].{allow_forwarded_traffic, allow_gateway_transit, use_remote_gateways}`, `provisioning.iso.image_uri`, `operations.updates.{install_after_deployment, target_version}`, `security.baseline_settings[]`, `identity.active_directory.precreate_computer_objects`, `hardware.sbe.{partner_properties[], partner_credentials[]}`, `devops.pipelines.{runner_label, environments.*}` (5.6.25), `devops.pipelines.{service_connection, variable_group}` (5.6.27, Azure DevOps only), and from 5.6.28 `azure.automation_identity.resource_group_roles[]`, `key_vaults[].{soft_delete_retention_days, allowed_ip_ranges}` (the vault Trailwright writes takes its retention from `cluster.key_vault.soft_delete_retention_days`, which it writes), `identity.active_directory.{forest_functional_level, domain_functional_level, dns_forwarders}`, `security.defender_for_cloud.{alert_notifications, alerts_to_admins}`, `network_devices[].{mtu, ports.*, ha.*}`, `landing_zone.policy.{assignments[], resource_group_assignments[]}`, `landing_zone.connectivity.{vpn_gateway.public_ip_name, vpn_gateway.secondary_public_ip_name, vpn_gateway.active_active, bastion.public_ip_name, nat_gateway.public_ip_name, nat_gateway.sku}`, `landing_zone.virtual_machines[].{dc_promotion, dsrm_password, os_disk_size_gb, os_disk_type, os_disk_caching, image_version}`, `devops.pipelines.{infrastructure_file, handoff_path, tool_versions.*}`, `devops.state.*` (`azure_local_key` and the state storage account settings), `devops.runners[].*` (admin account, NSG and managed identity names, disks, image, zones), `devops.runner_network.{hub_peering.spoke_name, hub_peering.hub_name, allow_internet_https, allow_internet_http, allow_icmp}` and `devops.runner_access.additional_role_assignments[]`. 5.6.26 added no key. Add them to the file by hand when the deployment needs them.

## Keys the toolkit removed

The export writes none of the keys the toolkit removed from schema 5. The toolkit's `config/variables/docs/MIGRATION.md` lists them for each version, and `REMOVED_KEYS` in `tests/infrastructureSchema.test.ts` holds the same list: the test checks that the vendored schema has none of them and that the export of every sample design writes none of them and no key the schema lacks. The resource provider list of the machine provisioning manifest is part of that JSON export, not of `infrastructure.yml`.
